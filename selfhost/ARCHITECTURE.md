# Архитектура

Где что живёт и почему именно так. Документ описывает боевую установку;
секреты (пароли, ключи, `.env`) сюда не попадают — репозиторий публичный.

## Общая картина

```text
        ritmup.ru ─── A ──▶ 194.113.38.147 (VPS, Debian, 2 GB RAM)
                                      │
                                      │  TCP 80 / 443  (только эти два порта наружу)
                                      ▼
                            ┌── selfhost-caddy-1 ──┐   HTTPS, сертификат Let's Encrypt
                            │   reverse_proxy      │   www → редирект на канонический хост
                            └──────────┬───────────┘
                                       │  внутренняя сеть Docker, app:3000
                            ┌──────────▼───────────┐
                            │    selfhost-app-1    │   Next.js 16, standalone-сборка
                            │  миграции при старте │
                            └──────────┬───────────┘
                                       │  db:5432, наружу не публикуется
                            ┌──────────▼───────────┐
                            │    selfhost-db-1     │   PostgreSQL 17
                            │  том postgres_data   │
                            └──────────────────────┘
```

Три контейнера поднимаются одним `compose.yaml` из каталога `/opt/ritmup/selfhost`
на сервере. Лимиты памяти: app 512 МБ, db 384 МБ, caddy 128 МБ.

## Важно: сервер общий

Этот VPS **не выделен под «Ритм»**. На нём параллельно работают другие сервисы
владельца, и они появились раньше. Из этого следуют жёсткие ограничения:

- **UDP 443 занят другим сервисом.** В `compose.yaml` порты Caddy опубликованы
  строго как `"80:80/tcp"` и `"443:443/tcp"`. Нельзя менять на `"443:443"` без
  суффикса `/tcp`: Docker тогда займёт и UDP, и чужой сервис отвалится.
  По той же причине не следует включать в Caddy HTTP/3.
- **TCP 8443–8446 заняты.** Не занимать их под что-либо своё.
- Памяти всего 2 ГБ и 512 МБ swap. Пересборка образа на сервере проходит, но
  впритык — не запускать сборку параллельно с другими тяжёлыми задачами.
- Перезапускать разрешено только контейнеры с префиксом `selfhost-`.
  `docker compose down` из каталога проекта безопасен, `docker restart` без имени
  или `docker system prune -a` — нет.

## Порты и firewall

UFW разрешает 22, 2228 и порты соседних сервисов, но **80 и 443 в списке UFW
отсутствуют**. Сайт всё равно доступен, потому что Docker публикует порты через
собственные цепочки iptables в обход UFW. Это ожидаемое поведение Docker, а не
ошибка настройки — но помнить о нём стоит: правилами UFW сайт не закрыть.

## Деплой

Сервер держит обычный git-клон репозитория, ветка `main`:

```bash
ssh -i ~/.ssh/finland_key root@194.113.38.147
cd /opt/ritmup && git pull
cd selfhost && docker compose up -d --build
```

Образ собирается прямо на сервере (`Dockerfile`, multi-stage, `output: standalone`).
Миграции применяются автоматически при старте контейнера: команда в `Dockerfile`
проверяет наличие `BETTER_AUTH_SECRET` и `DATABASE_URL`, затем запускает
`scripts/migrate.mjs` и только после этого `server.js`. Применённые файлы
отмечаются в таблице `schema_migrations`, повторно не выполняются.

Каталог принадлежит пользователю `deploy` (uid 1000, состоит в группе `docker`).

## Конфигурация

`.env` лежит только на сервере, в репозитории есть лишь `.env.example`.
Значимые переменные: `APP_DOMAIN`, `BETTER_AUTH_URL`, `BETTER_AUTH_SECRET`,
`DATABASE_URL` и пара `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` (пока пустые,
`NEXT_PUBLIC_GOOGLE_AUTH_ENABLED=false`).

`NEXT_PUBLIC_*` вшивается в бандл на этапе сборки, поэтому включение Google-входа
требует пересборки образа, а не только правки `.env`.

## Данные

Всё живёт в томе `postgres_data`. Схема разложена по файлам в `migrations/`:

- `001_auth.sql` — таблицы better-auth (пользователи, сессии, аккаунты);
- `002_app.sql` — профили, дневные записи, еда, дружба, лента событий;
- `003_healthkit.sql` — отметка времени синхронизации с Apple Health;
- `004_health_tokens.sql` — шаги, минуты активности и ключи для «Быстрых команд».

Список еды за день пока хранится в `localStorage` браузера, на сервер уходят
только агрегаты в `daily_logs`. Таблица `food_entries` заведена, но приложение
её ещё не использует.

**Резервных копий сейчас нет.** Скрипт `scripts/backup.sh` написан, но в cron не
добавлен, и выгрузки за пределы VPS не настроено.

## Что снаружи

- `ritmup.ru` — A-запись на IP сервера, работает.
- `www.ritmup.ru` — A-записи **нет**, при этом `Caddyfile` держит для неё
  редирект. Пока запись не появится, Caddy не сможет получить сертификат на `www`.
